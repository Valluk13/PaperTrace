# PaperTrace

Система собирает литобзор по теме из статей arXiv, отсеивает ненадёжные препринты и проверяет каждое утверждение
по странице PDF. Цель КП2: измерить, насколько проверка утверждений повышает **дословную проверяемость** тезисов
(существование ссылки, поддержка текстом страницы, точность адресации) по сравнению с обычным чатом и обычным RAG —
и честно отделить этот эффект от «правдивости» на глазах судьи, оценивающего только смысл (проверка круговости метрики).

## Как запустить (один раз настроить, потом одна команда)

Нужен Python 3.10 или новее.

    git clone <ссылка на ваш репозиторий>
    cd papertrace
    python -m venv .venv
    .venv\Scripts\activate          # Windows
    source .venv/bin/activate       # Mac / Linux
    pip install -r requirements.txt
    copy .env.example .env          # Windows (на Mac/Linux: cp .env.example .env)

Откройте `.env` и впишите ключ и модель (`LLM_API_KEY`, `LLM_MODEL`), ключ OpenAlex и (для бенчмарка) `JUDGE_MODEL`.
Файл `.env` нельзя коммитить, он уже в `.gitignore`.

    python agent_graph.py "ваша тема обзора"                 # полный PaperTrace (режим C)
    python agent_graph.py "тема" --no-filter --no-verifier    # обычный RAG (режим B)
    python preflight.py eval_dataset_big.json                 # перед прогоном: arXiv, диск, узлы, модели
    python preflight.py eval_dataset_big.json --guard          # и прогон guard'ом по всем темам (1 запрос на тему)
    python eval_benchmark.py --dataset eval_dataset.json --limit 3   # бенчмарк трёх режимов
    python eval_draft.py --results eval_results.json          # метрика C по черновику (пара к B, без писателя)
    python -m unittest discover tests                         # быстрые тесты (офлайн, ни одного запроса)

Без файла узла граф останавливается с внятным текстом, а не молча: прогон на заглушках измерял бы заглушки.
Для локальной разработки без чужих файлов включите заглушки явно: `ALLOW_MOCKS=1 python agent_graph.py "тема"`.

Ночной прогон сам смотрит на свободную память и останавливается на границе темы, когда остаётся меньше
`MEM_FLOOR_MB` (по умолчанию 900 МБ, меняется переменной окружения `MEM_GUARD_MB`). Ячейки к этому моменту
уже записаны, поэтому повторный запуск той же командой добирает недостающее бесплатно. Причина в том,
что векторный поиск прибавляет несколько мегабайт на каждую тему и не отдаёт их обратно.

## Кто за что отвечает

| Файл | Владелец | Функция узла | Метрика |
|---|---|---|---|
| `state.py`, `common.py`, `agent_graph.py` | Тимлид | `planner_node`, сборка графа | время и токены на один обзор |
| `arxiv_searcher.py` | Data Engineer | `arxiv_search_node` | `evaluate_search_recall` |
| `reliability_rag.py` | RAG & Vector DB | `reliability_and_rag_node` | `evaluate_reliability_filter` |
| `verifier_api.py` | Backend & Security | `security_guard_node`, `writer_verifier_node` | `unsupported_rate` |
| `eval_benchmark.py`, `eval_draft.py` | Eval & QA Lead | скрипты | таблица по режимам A/B/C (+ C по черновику), статус каждой ячейки |

Контракт: узел принимает состояние графа и возвращает словарь только с теми полями, которые изменил,
плюс `latency_sec` и `total_tokens` за свой узел. Поля описаны в `state.py`.

## Работа с Git

У каждого своя ветка (`feature/<роль>`) и свой файл. Изменения идут через pull request, тимлид проверяет и
нажимает Merge. Файл `state.py` без согласования с тимлидом не меняем.

## Известные ограничения (продублированы в report.md)

- Номера страниц это номера страниц PDF-файла, а не печатные номера на листе.
- Писатель видит первые 25 страниц каждой статьи (`MAX_PAGES`), судья проверяет по 60 (`JUDGE_MAX_PAGES`):
  тезис с страницы 40 — это «страница указана неверно», а не «статьи нет».
- `claim_support_rate` засчитывает подтверждение, найденное на ЛЮБОЙ из 3 похожих страниц, поэтому он всегда
  выше `page_accuracy_rate`. Строгая метрика — `page_accuracy_rate`; публиковать support без неё нельзя.
- Существование ссылки = статья с таким ID скачивается с arXiv. Это не доказывает, что утверждение относится к той самой статье.
- У режима A обе метрики поддержки около нуля по построению: модель угадывает номера страниц, которых не видела.
  Сравнение A↔C честно только по существованию ссылок.
- Режимы могут терять темы по-разному (guard блокирует запрос только в B/C). Сравнивать нужно таблицу 2
  в `results_table.md` — она посчитана строго по темам, где данные есть у всех режимов.
- Судья это LLM, поэтому его согласие с человеком нужно проверить вручную на 30-40 утверждениях.
- Внутренний верификатор и судья требуют один и тот же признак (непрерывная цитата не короче 25 знаков),
  поэтому финальный обзор C уже отобран под ту самую метрику, которой его измеряют. Честная пара для B —
  `mode_c_draft` из `eval_draft.py` (те же тезисы до отсева); финальный C показывает лишь цену верификатора.
- Векторный поиск на ephemeral-индексе не отдаёт память обратно: на замере 30 вызовов узла прирост ~180 МБ
  (примерно 6 МБ на тему в двух режимах). На слабой машине прогон встанет посередине — для этого и охрана памяти.
- Бесплатные модели и лимиты меняются; при ошибках 429 увеличьте `LLM_SLEEP` и `JUDGE_SLEEP`.
