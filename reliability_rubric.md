# Рубрика ручной разметки фильтра надёжности (роль: RAG & Vector DB)

Цель: получить «золотые» метки человека на 20 скачанных статьях и посчитать, насколько программный
фильтр из `reliability_rag.py` совпадает с человеком. Это и есть метрика участника 3 для отчёта.

## Процесс (2 человека, ~1 час)

1. Получить выгрузку скачанных статей в `papers.json` (см. раздел ниже).
2. `python reliability_rag.py make-template papers.json reliability_labels.csv` — скрипт сам создаст
   CSV со списком статей.
3. Каждый разметчик независимо открывает статью (аннотация + первые 2–3 страницы: разделы
   Methods/Experiments и таблицы результатов) и ставит `good` или `trash` в своей колонке
   (`rater1`, `rater2`) строго по критериям ниже, не подглядывая друг в друга.
4. Разметчики сверяются. В `final_label` ставится согласованный вердикт; спорные случаи
   обсуждаются, и итоговое решение с одной строкой обоснования пишется в `comment`.
5. `python reliability_rag.py evaluate papers.json reliability_labels.csv` — скрипт прогоняет статьи
   через тот же фильтр, что и в графе, и печатает TP/FP/FN, Precision, Recall, F1 и список
   расхождений «программа vs человек». Этот вывод идёт в отчёт; каждое расхождение разбирается
   (кто прав и почему).

## Критерии: когда ставить good / trash

**good (надёжная)** — выполняется вариант А или Б:

- **А. Эмпирическая работа**: описан эксперимент — есть конкретные данные или выборка (что за данные,
  сколько примеров) И результаты численно сравнены хотя бы с одним бейзлайном/аналогом (есть таблица
  или числа «наш метод vs другой»). Плюсом, но не обязательно: ссылка на код или данные
  (github/gitlab/huggingface/zenodo), раздел Limitations.
- **Б. Обзор (survey) или теоретическая работа**: собственных экспериментов по определению нет, зато
  систематически и структурированно разбираются существующие методы/результаты других. Отсутствие
  кода и бейзлайнов в этом случае мусором не считается.

**trash (мусор)** — типичные признаки нейрослопа: общие слова без проверяемого метода; нет ни данных,
ни сравнений; «результаты» без чисел и таблиц; список литературы с нерелевантными/несуществующими
источниками; текст повторяет сам себя, картинки-заглушки.

## Что именно проверяет программа (для разбора расхождений)

| Признак PaperMeta | Как получается |
|---|---|
| `has_code_link` | regex по github/gitlab/huggingface/zenodo в тексте |
| `paper_type`, `has_dataset`, `has_baseline_comparison` | один вопрос LLM по аннотации и первым 2 страницам |
| `has_limitations` | слово limitations в тексте |
| `venue` | поле из OpenAlex (проставляет участник 2) |

Итоговый балл (порог 0.5): у эмпирических — код 0.30, датасет 0.20, сравнение с аналогами 0.25,
limitations 0.15, публикация вне arXiv 0.10; у обзоров/теории — база 0.6 + 0.2 за venue + 0.1 код +
0.1 limitations. Веса и порог — командное решение, в отчёте их нужно обосновать (например: сравнение
с бейзлайнами весит больше, чем наличие ссылки на код, потому что код без численных результатов не
доказывает пользу метода). Если разметка покажет много FP/FN одного типа — это аргумент пересмотреть
веса, и это тоже пишем в отчёт.

## Как получить papers.json

Статьи приходят из узла `arxiv_search_node` (файл `arxiv_searcher.py`, участник 2). Если файл ещё
не в репозитории — попросить у Data Engineer выгрузку, либо выгрузить состояние после запуска графа:

```python
from agent_graph import run_pipeline
import json

res = run_pipeline("ваша тема обзора")
with open("papers.json", "w", encoding="utf-8") as f:
    json.dump([p.model_dump() for p in res["found_papers"]], f, ensure_ascii=False, indent=2)
```

Для разметки достаточно, чтобы у статей были заполнены `abstract` и `pages_text` (текст страниц PDF) —
именно их читает и человек, и программа. Нужны минимум 20 статей; если после фильтра граф их
отбросил, в `res["found_papers"]` они всё равно есть (с проставленными `is_reliable`).
